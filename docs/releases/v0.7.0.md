## v0.7.0 (unreleased)

### Simulate time

- **Virtual server clock (#230).** `EmbeddedServerHost.UseVirtualClock(tickMs)` makes ticks, not the wall clock, drive the server's time until the returned `VirtualClock` is disposed. Each `Tick()` moves it by exactly `tickMs`.
  - Server systems, tick listeners, delayed callbacks, `world.ElapsedMilliseconds`, the uptime and, by default, the calendar all follow it. Hunger, AI, block entity ticks and entity physics therefore advance by simulated time on any machine.
  - `clock.Advance(span)` ticks in steps of 250 ms or less, because entity physics drops time past 0.4 s.
  - Disposing goes back to the wall clock without a jump. A clock a test leaves in use ends with the test.
  - The clock is recorded in `run.json` as `serverClock`.
- **Wait for background work (#230).** `EmbeddedServerHost.WaitForBackgroundWorkAsync()` waits until relight, chunk loading and generation, random block ticks, the creature spawner and async pathfinding have no work queued. These threads keep running on real time.
- **Server tick listeners and fast-forward (#233).**
  - `Host.TickListeners` lists the server's game tick listeners and delayed callbacks by position, entity, mod or owner type. Each one comes with its interval, when it last ran, its handler and its owner.
  - `FastForwardAsync(pos, span, step)` runs the ones at a block position on simulated time, at once. A firepit cooks and a quern grinds as far as they would in that time, without waiting real seconds, and the next tick owes them only what was left over.
  - `PharosAssert.NoTickListenersAt(host, pos)` catches listeners a block entity leaves behind when it is removed.
- See the "Virtual Clock" and "Tick Listeners and Fast-Forward" sections of `docs/writing-server-scenarios.md`.

### Inspect the game

- **Game event recorder (#232).** `Host.Events.Record(filter)` and `Client.Events.Record(filter)` return a disposable log of the game's own events, as typed records in firing order, each with its tick or frame.
  - Server: blocks placed, broken and used; players dying, respawning, changing game mode or hotbar slot, and interacting with entities; spawn attempts; chunk columns loaded and unloaded; world saves.
  - Both sides: entities spawning, dying, despawning, mounting and unmounting; map regions loaded.
  - `WaitForAsync<T>(predicate, since)` steps until a matching record appears; a server log inside a client-server session steps the whole session. `Mark()` gives a `since`.
  - `PharosAssert.EventOrder(log, ...)` checks the order, with record types or `EventMatch.Of<T>(predicate)`.
  - A log a test leaves open is closed when the scenario ends, before the rollback. See `docs/inspection-api.md`.

### Fixes

- **Server datagrams sent over TCP (#232).** An engine-mode client in a loopback session no longer crashes its frame with `NotImplementedException` when the server falls back to sending its UDP packets, such as entity positions, inside TCP packets. The link now delivers them.
