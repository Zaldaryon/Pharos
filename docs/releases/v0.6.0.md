## v0.6.0 (unreleased)

### Diagnose failures

- **Failure artifacts (#190).** A failing or timed-out scenario saves the following under `PHAROS_ARTIFACTS`:
  - a screenshot of the last frame;
  - the client and server logs, plus the game's own log files;
  - the traffic, when asked;
  - a `run.json` with the test, the outcome, the versions, the world and the run.

  The failure message lists where they are and the errors logged. `PHAROS_KEEP_SANDBOX=1` keeps the sandbox, and CI uploads the folder for a failed job. See `docs/failure-artifacts.md`.
- **Scenario watchdog (#190).** `TimeoutMs` on the scenario attributes is now enforced; it was documented but never applied. A body that runs out of time is stopped at its next step into the game and torn down. A body that does not stop, or a game thread that is stuck, makes later scenarios fail at once instead of hanging. `PHAROS_TIMEOUT_SCALE` stretches every limit on slow machines. `[ClientScenario]` and `[ClientTheory]` gain `TimeoutMs`, 120 seconds by default.

### Breaking changes

- **Enforced timeouts:** scenario bodies that ran longer than their `TimeoutMs` (120 seconds, or 180 for client-server scenarios) used to pass and now fail. Raise `TimeoutMs`, set it to 0, or set `PHAROS_TIMEOUT_SCALE`.
- **Failure type:** a failing scenario reports a `ScenarioFailedException`, whose message starts with the original exception's type and message and whose stack trace is the original one. The original exception is in `ScenarioFailedException.Failure`.
- **`FailOnLoggedErrors` timing:** in tests run by the scenario attributes, logged errors are checked when the test body ends, before teardown, rather than in `DisposeAsync`.
