## v0.6.0 (unreleased)

### Diagnose failures

- **Failure artifacts (#190).** A failing or timed-out scenario saves the following under `PHAROS_ARTIFACTS`:
  - a screenshot of the last frame;
  - the client and server logs, plus the game's own log files;
  - the traffic, when asked;
  - a `run.json` with the test, the outcome, the versions, the world and the run.

  The failure message lists where they are and the errors logged. `PHAROS_KEEP_SANDBOX=1` keeps the sandbox, and CI uploads the folder for a failed job. See `docs/failure-artifacts.md`.
- **Scenario watchdog (#190).** `TimeoutMs` on the scenario attributes is now enforced; it was documented but never applied. A body that runs out of time is stopped at its next step into the game and torn down. A body that does not stop, or a game thread that is stuck, makes later scenarios fail at once instead of hanging. `PHAROS_TIMEOUT_SCALE` stretches every limit on slow machines. `[ClientScenario]` and `[ClientTheory]` gain `TimeoutMs`, 120 seconds by default.

- **Boot diagnostics (#189).** `EmbeddedServerHost.BootDiagnostics` and `HeadlessClient.BootDiagnostics` list every warning, error and fatal error logged while booting, each with its `Source`.
  - `[StrictBoot]` fails the boot of a class that logged anything its `[AllowBootDiagnostic(pattern, Level, Source, Count, Required)]` allowances do not cover. The failing test gets `boot-diagnostics.txt` among its failure artifacts, and the class's other tests fail at once without booting again.
  - Scenario classes expose `UnexpectedBootDiagnostics`.
  - See `docs/boot-diagnostics.md`.
- **No mod safety check (#189).** Hosts booted by Pharos no longer fetch the list of blocked mods from the game's website. Offline, that fetch cost up to 30 seconds on the first boot of a test run and logged warnings.

### Smoke-test a mod

- **`pharos smoke` (#203).** A new `Zaldaryon.Pharos.Cli` dotnet tool provides the `pharos` command. `pharos smoke --mod mymod.zip [--strict] [--command ...] [--frames n]` boots a server and a client with the mods, joins, walks and looks around, and fails on a crash, a timeout, a failed command, a logged error or, with `--strict`, a boot warning.
  - Exit codes: 0 passed, 1 failed, 2 could not run.
  - The tool ships none of the game's files: it runs against your own install.
- **`ModSmokeTest` (#203).** The same smoke test as a scenario class: `public class Smoke : ModSmokeTest;` with `[ServerMods]`.
- **Overridable scenario inputs (#203).** `ClientServerScenarioBase` takes its mods and its strictness from virtual properties (`ServerModPaths`, `ClientModPaths`, `StrictBoot`, `BootAllowances`), so a subclass can set them in code.
- See `docs/smoke-test.md`.

### Drive the client

- **Client commands (#183).** `HeadlessClient.Commands` runs a client's dot commands as the chat dialog does and returns their status, message, error code, data and the chat lines they showed. `ExecuteSuccessAsync` throws unless the command succeeded or was deferred, and a command whose arguments are looked up later is waited for. See "Client commands" in `docs/engine-mode.md`.
- **Hotkeys (#184).** `HeadlessClient.Hotkeys` lists every registered hotkey with its default and current binding, fires one by its code through the real gating (`TriggerAsync`) or by pressing its keys (`PressAsync`), rebinds one as the controls menu does, and lists hotkeys that share a binding. See "Hotkeys" in `docs/engine-mode.md`.
- **Input (#184).** `VirtualInputController` sends Shift, Ctrl and Alt with mouse buttons, presses the side buttons (`InjectMouseButton(EnumMouseButton, ...)`), and gives a key pressed right after another the second key the game's double-tap bindings read.

### Isolate tests

- **Mods take part in rollbacks (#186).** `pharos:rollback:captured` and `pharos:rollback:restored` fire on the server's and the client's event bus around a rollback, and scenario classes can override `OnRollbackCaptured()` and `OnRollbackRestored()`. A rollback removes the tick listeners, delayed callbacks and event-bus listeners a test registered, on both sides, and the block-position callbacks that would carry on undone changes.
- **Isolation report (#186).** `Isolation` tells each test how its hosts were made ready (first boot, rolled back, recycled or booted again, and why), with the chunks and listeners a rollback took and its time. Each test's output says how it was made ready and how it left the hosts, with a running summary of its class. `[ServerWorld(StrictIsolation = true)]` fails a test whose world cannot be rolled back. See `docs/writing-server-scenarios.md`.
- **`[ServerWorld]` on client-server classes (#186).** `ClientServerScenarioBase` now reads its isolation and its world from `[ServerWorld]` when the class has one; it used to ignore the attribute.

### Control time and weather

- **Calendar (#185).** `EmbeddedServerHost.Calendar` reads the time, date and season and sets them: `SetTime`, `SetDate`, `Advance`, `Freeze` and `Unfreeze`. Changes land on whole seconds and reach clients at once.
- **Weather (#185).** `EmbeddedServerHost.Weather` sets cloud patterns and wind for every loaded region or the four around a position, overrides precipitation, and stops or resumes the weather's own changes.
- **Calendar sync (#185).** `ClientServerLoopbackSession.WaitForCalendarSyncAsync()` waits until the client's calendar matches the server's.
- **Rollback (#185).** A rollback restores the calendar and the weather, and a client-server rollback waits for the client's calendar. See "Calendar and Weather" in `docs/writing-server-scenarios.md`.

### Configure mods

- **Data files (#187).** `[DataFiles]` copies files such as mod configs into the server's or the client's data folder before they boot, on a class or a single test. `{{pharos:port:NAME}}` placeholders become free ports, the same on both sides, and `DataFilePort("NAME")` reads them back. Hosts are pooled by their files, and a rollback puts changed files back. See `docs/data-files.md`.
- **Each side's data folder (#187).** A server's mod API (`DataBasePath`, `GetOrCreateDataPath`, `LoadModConfig`, `StoreModConfig`) now uses the server's data folder after a client has booted in the same process; it used to use the client's.

### Run faster

- **Parallel runs (#192).** `pharos run <tests> --parallel N`:
  - lists the tests without booting anything, and gives each live class a worker process of its own; the other tests share one;
  - runs N workers at a time, each with its own data folders, ports, virtual display under Linux, and share of the cores;
  - merges their results into one TRX and one summary, or JSON lines with `--json`.

  A worker that crashes or hangs fails its class, never the whole run. `--list` shows the groups. See `docs/parallel-runs.md`.
- **Staging in parallel (#192).** Test processes that start in the same output folder at once no longer race to link or copy the game's `Lib`, `Mods` and `assets` folders into it.

### Fixes

- **Server console commands (#203):**
  - `ServerScenarioBase.ExecuteCommand` dropped the first letter of the command name and ran without the console's privileges, and `CommandResult.Ok` counted an unknown command as success. As a result, `ExecuteSuccess("/time set day")` never ran the command, yet passed.
  - Commands now run as the game's own console runs them, and `Ok` is true only for success or a deferred result.

### Breaking changes

- **Rollback rewinds time:** the calendar and the weather go back to how they were after boot between the tests of a rolled-back class. Data mods keep in the save game is not rewound with them.
- **`[ServerWorld]` on a `ClientServerScenarioBase` class** now takes effect: its seed, play style, world type and isolation apply, and the world is named after the class.

- **Enforced timeouts:** scenario bodies that ran longer than their `TimeoutMs` (120 seconds, or 180 for client-server scenarios) used to pass and now fail. Raise `TimeoutMs`, set it to 0, or set `PHAROS_TIMEOUT_SCALE`.
- **Failure type:** a failing scenario reports a `ScenarioFailedException`, whose message starts with the original exception's type and message and whose stack trace is the original one. The original exception is in `ScenarioFailedException.Failure`.
- **`FailOnLoggedErrors` timing:** in tests run by the scenario attributes, logged errors are checked when the test body ends, before teardown, rather than in `DisposeAsync`.
- **Logs after a strict boot:** a `[StrictBoot]` class whose boot passes clears its hosts' logs, so `FailOnLoggedErrors` no longer sees the boot's errors in its first test.
- **`CommandResult.Ok`:** false for `NoSuchCommand` (it was true), so `ExecuteSuccess` fails on an unknown command.
- **Commands run for real:** `ExecuteCommand`, `ExecuteSuccess`, `ExecuteCommandAsPlayer` and `ExecuteSuccessAsPlayer` now run the command they are given: the console ones as an admin, the player ones with the player's privileges. Tests that passed only because nothing ran may now fail.
